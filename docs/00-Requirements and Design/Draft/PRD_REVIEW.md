# 今日热搜 · PRD 评审意见

评审对象：

- `RESEARCH.md`
- `PRD.md`

评审日期：2026-06-03

## 总体结论

当前 PRD 的方向成立，差异化也清楚：「用 AI 读懂热搜」比普通热榜聚合更有记忆点，AI 推荐卡片和 AI 分类标签能形成明确卖点。

但这份 PRD 目前更像「理想 MVP」，还没有完全收敛到「可稳定交付的第一版」。主要风险集中在平台接入范围、AI 能力验收、接口契约和异常态定义上。

建议在进入技术设计和开发拆分前，先完成一次 PRD 收敛：降低高风险平台对 MVP 成败的影响，补齐 AI 输出格式和验收标准，明确接口数据结构与降级策略。

## 高优先级问题

### 1. MVP 范围偏大，抖音风险与成功指标冲突

PRD 将「首页 8 平台卡片全部展示真实数据」作为成功指标，但需求研究中已经明确抖音数据获取难度高、反爬强度极高，可能需要逆向签名或第三方 API。

这会导致一个问题：即使其他 7 个平台和 AI 功能都完成，只要抖音接入不稳定，MVP 也会被判定为失败。

建议调整：

- 将抖音从「MVP 必须稳定接入」改为「MVP 尽力接入，可降级平台」。
- 成功指标改为「核心 7 平台稳定展示真实数据，抖音有可解释的降级方案」。
- 在 PRD 中为抖音单独定义降级方案，例如：
  - 暂时隐藏抖音卡片；
  - 显示「数据源维护中」；
  - 使用第三方 API 作为可选方案；
  - 或在首版先用 Mock / 占位数据，但必须明确标注。

### 2. AI 推荐卡片缺少可测验收标准

PRD 要求 AI 实现跨平台事件聚类、智能推荐、推荐理由和情感倾向，但没有定义什么叫「推荐正确」、什么叫「聚类正确」、什么叫「情感判断可接受」。

这会影响后续开发和验收：AI 输出看起来合理，但无法判断是否达标。

建议补充：

- AI 输入字段：
  - 平台；
  - 排名；
  - 标题；
  - 热度值；
  - 原链接；
  - 抓取时间。
- AI 输出字段：
  - 事件标题；
  - 推荐等级；
  - 推荐理由；
  - 涉及平台；
  - 情感倾向；
  - 关联热搜条目；
  - 置信度或可选备注。
- AI 推荐验收标准：
  - 输出 5 到 8 条事件；
  - 同一明显事件不重复出现；
  - 推荐理由必须引用可解释依据，例如「多平台同时出现」「排名靠前」「热度值较高」；
  - 情感倾向只允许正面 / 中性 / 负面，无法判断时默认中性；
  - AI 返回格式异常时不影响基础热搜展示。

### 3. 成功指标偏功能清单，不够产品化

当前成功指标主要是「能展示、能输出、能访问」。这些适合做工程验收，但还不足以验证产品目标「帮助用户 3 分钟内掌握全网正在发生什么」。

建议保留现有工程指标，同时增加产品体验指标：

- 首页首屏加载时间小于 2 秒；
- 数据更新时间不超过 10 分钟；
- 用户无需登录即可完成浏览；
- AI 推荐卡片在移动端首屏可读；
- 用户能在 3 分钟内读完 5 到 8 条核心推荐；
- AI 分类标签覆盖率大于 90%；
- 标签筛选后无结果时有明确空状态。

### 4. 数据接口缺少基础契约

PRD 中定义了 `/api/hot` 和 `/api/hot/:source`，但没有说明返回字段、错误格式、空数据格式和 AI 不可用时的数据结构。

这会导致前后端实现时出现理解偏差。

建议在 PRD 中加入最小接口契约，例如：

```json
{
  "updatedAt": "2026-06-03T10:00:00Z",
  "ai": {
    "available": true,
    "recommendations": []
  },
  "sources": [
    {
      "source": "weibo",
      "name": "微博",
      "listName": "热搜榜",
      "status": "ok",
      "updatedAt": "2026-06-03T10:00:00Z",
      "items": [
        {
          "rank": 1,
          "title": "示例热搜标题",
          "url": "https://example.com",
          "heat": "123万",
          "tags": ["社会"]
        }
      ]
    }
  ]
}
```

同时建议定义错误态结构：

```json
{
  "source": "douyin",
  "name": "抖音",
  "status": "error",
  "errorMessage": "数据源暂时不可用",
  "items": []
}
```

### 5. 目标用户定义略混杂

PRD 将「想快速了解全网热点的上班族、学生、信息工作者」作为主要用户，同时将「对 Vibe Coding / 全栈开发感兴趣的学习者」作为次要用户。

这两类人关注点不同：

- 前者是产品真实使用者，关心信息效率；
- 后者更像项目读者或教程受众，关心开发过程和学习价值。

建议拆分：

- 产品目标用户：上班族、学生、信息工作者；
- 项目展示受众：Vibe Coding 学习者、全栈开发学习者。

这样可以避免首页功能和文案同时服务两类目标，导致产品定位变散。

## 中优先级问题

### 6. 异常态还需要补齐

PRD 已经包含单平台失败、AI 不可用、后端整体不可用，但仍建议补充以下状态：

- 首次加载中；
- 标签筛选无结果；
- 缓存已过期，但新一轮抓取失败；
- 平台返回空列表；
- 热度值缺失；
- 原链接缺失；
- AI 返回 JSON 格式异常；
- 部分热搜没有标签；
- 用户点击刷新后仍失败。

这些异常态会直接影响前端实现和用户体验。

### 7. 「刷新按钮」行为需要明确

页面结构里提到了刷新按钮，但 PRD 未定义刷新行为。

建议明确：

- 普通用户点击刷新：重新请求 `/api/hot`，但不强制绕过后端缓存；
- 开发环境 `?refresh=1`：允许跳过缓存；
- 刷新中需要 loading 状态；
- 刷新失败时保留旧数据，并显示轻量提示。

### 8. AI 分类标签需要定义兜底规则

PRD 只说明标签由 AI 生成并缓存，但没有说明 AI 无法分类时怎么办。

建议补充：

- 每条热搜最多 2 个标签；
- 无法判断时使用「其他」或空标签；
- 标签必须来自固定枚举；
- 前端只展示固定枚举内的标签；
- AI 返回非法标签时后端过滤。

## 低优先级建议

### 9. 合规说明可以更明确

当前页脚合规方向是对的，但建议增加两点：

- 原文链接跳转到来源平台；
- 本站不对 AI 生成推荐和标签作事实保证。

### 10. 技术栈可保留，但部署方案不宜过早锁死

PRD 写了 Vercel + Railway，不强制统一。这个表述可以保留。

如果后续技术设计发现后端定时任务、缓存、第三方 API 密钥管理更适合单体部署，也可以调整为 Render、Railway、Fly.io 或其他方案。

## 建议修改顺序

1. 收缩 MVP 验收口径：明确 7 个核心平台稳定，抖音可降级。
2. 补充 AI 输出 JSON、异常处理和验收标准。
3. 补充 `/api/hot` 与 `/api/hot/:source` 的基础数据结构。
4. 拆分产品目标用户和项目展示受众。
5. 补齐加载、空状态、缓存过期、AI 格式异常等边界状态。
6. 更新成功指标，让它同时包含工程验收和产品体验。

## 推荐后的 MVP 定义

建议将 MVP 重新表述为：

> 今日热搜首版是一个无需登录、可公网访问的 AI 增强热榜聚合网站。它稳定展示微博、知乎、B站、澎湃新闻、36氪、虎扑、GitHub 的实时热榜，并尽力接入抖音；通过 AI 生成今日推荐和分类标签，帮助用户在 3 分钟内理解全网核心热点。AI 或单个平台不可用时，基础热榜浏览不受影响。

这个版本更容易交付，也更符合当前研究中识别出的技术风险。
